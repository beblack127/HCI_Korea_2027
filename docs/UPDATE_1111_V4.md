# 11.11-v4 — 탐색 진전, 관점 정정과 응답 반복

## 문제와 변경

기존 구현은 연구 문제의 직접 발화 인정 여부를 탐색의 진전 표현에도 사용했다. 범위를 좁혀 검토하는 행동이 있어도 문제 문장 검증을 통과하지 못하면 판단 유보만 반복됐다. 또한 같은 주제 안의 관점 정정이 일반적인 입력 추가로 표현되거나, 부정한 이전 관점이 현재 관심으로 남았다. 일반 추천/구체화는 반복 후보의 생성 후 검사 대상이 아니었다.

이번 변경은 단일 세션의 실제 검토 흐름과 명시적인 연구 문제를 분리한다. 어려움의 판정 기준, 후보 선택 버튼, UI 디자인은 유지한다.

### 관찰 가능한 진전

`core/progress.py`의 `exploration_progress`는 initial/reviewing/narrowing/revising이라는 **관찰한 검토 흐름**을 기록한다. 선택·둘러보기·구체화 요청이 근거이며 이해, 확정, 연구의 완성도를 의미하지 않는다. 별도의 `problem_status`는 직접 발화에서 연구 문제를 확인했는지 나타낸다.

- 패널의 단계 배지와 현재 방향, 대화 요약은 최근 실제 선택/정정한 관점을 우선한다.
- 명시적인 연구 문제가 없어도 구체화 요청을 관찰한 사실은 표시한다.
- 지원의 범위 선택에도 관찰된 구체화 흐름을 반영한다. 둘러보기/구체화하기의 명시 행동은 계속 우선한다.
- 과거 저장된 상태·응답·원본 추정은 재작성하지 않는다. 새 턴의 추정부터 새 정책이 적용된다.

### 연구할 현상의 근거

모델은 `problem_basis`로 현상/관계/설계 목적, 대상·현상·상황의 원문 부분을 제안한다. 서버는 해당 실제 사용자 입력과 원문 구간을 확인한다. 현상 연구에 ‘영향/차이’ 같은 표현을 필수로 요구하지 않는다.

모델이 조사·어미를 바꾸거나 원문 요소를 재배열한 경우에도 내용 단어가 모두 실제 원문에 있는지 확인하고 가장 짧은 실제 구간으로 연결한다. 원문에 없는 도메인·조건·대상은 추가하지 않는다. 이는 의미적 정답 보장이 아닌 검증 가능한 근거 연결이다. 일반 관심사/일반 도움 요청/카드 설명을 연구 문제로 자동 승격하지 않는다.

### 관점 정정

`focus_update`는 같은 주제 안의 add/refine/replace/compare를 기록한다. 최신 입력의 정확한 인용과 원문 구간을 검증한다. 명확한 대조 문장에는 원문 추출 보완 경로가 있다.

- 정정은 `topic_relation`의 주제 전체 변경과 별개다.
- 정정 전 관심은 `superseded_focuses`와 이력에 남기고 현재 관점에서 제외한다. 부정·정정 문장을 긍정적인 현재 관심으로 재사용하지 않는다.
- 이전 버전 세션을 이어갈 때도 로그에 있는 명시적인 정정을 재구성하므로 과거 관점이 다시 살아나지 않는다.
- 정정에는 어려움 판정 없이도 짧은 직접 답변을 제공한다. 지원 불일치와 사용자 어려움을 구별한다.

### 생성 직후 반복 검사

`completed_response_issues()`를 일반 추천과 구체화에도 적용한다. 완료된 응답의 같은 제목/설명 묶음, 제목만 바꾸고 유지한 설명, 변경 없이 다시 추천한 선택 부모를 검사한다. 문제가 있으면 같은 턴에서 최대 1회 보완한다. 제공자 오류를 자동 재시도하지 않는다.

개념 설명·기존 후보 비교에서는 유용한 후보 유지가 허용된다. 구체화에서도 제목이 같아도 설명에 새로운 검토 정보를 제공하면 무조건 거절하지 않는다. 이 검사는 의미적 품질 전체를 보장하지 않는다.

`response_quality`와 `response_validation` 기록에 시도/문제/보완 결과를 남긴다. 방금 생성한 응답을 포함해 `support_issues`를 다시 계산하며, 현재의 반복 문제를 다음 턴까지 늦추지 않는다. 반복은 시스템 문제로 다루고 사용자 어려움의 근거로 바꾸지 않는다.

## 검증

- Python 146개: 기존 124개 + 신규 22개 통과.
- JavaScript 31개: 기존 29개 + 신규 2개 통과.
- 실제 문제 세션의 11개 원본 추정을 새 검증/표현으로 오프라인 재처리하여 검토/범위 축소/관점 정정이 구분되고, 정정 전 관점이 활성 관심에 남지 않는 것을 확인했다. 원본 DB는 수정하지 않았다. 로그 사본과 원본 대화는 공개 저장소에 포함하지 않는다.
- 새 검증은 직접 문제 표현과 검토 흐름을 구별하는 대비 사례, 원문에 없는 역할/관점 거절, 정정 이력 유지, 후보 반복의 같은 턴 보완, 설명·비교의 후보 유지, UI 표현을 포함한다.

실제 Gemini 최종 연속 검사 6턴이 모두 HTTP 200으로 완료됐다. 현상 서술의 근거 연결, 관심 정정, 둘러보기, 구체화, 개념 설명을 점검했고 매 턴 후보 3개를 유지했다. 정정 턴은 직접 답변을 제공하며 이전 이해도 관점이 현재 관심에서 빠졌고, 구체화 턴은 관찰된 narrowing과 최근 선택 제목을 표시했다. 문제 문장 인정 여부와 검토 진전이 독립적으로 표시됐다.

최종 검사 중 한 턴은 제공자 응답에 약 93초가 소요됐다. API 지연의 변동성은 남아 있으며 기존 300초 타임아웃/경과시간 표시를 유지한다. 인위적인 대기나 자동 모델 변경은 추가하지 않았다. 추출 필드의 원문 불일치와 정정 전 관점 잔류는 실제 API 검사 중 발견해 재현 검사를 추가한 뒤 위 최종 실행으로 다시 확인했다.

배포 후 실제 Chrome에서 합성 API 실행의 저장 결과를 렌더링하여 관점 조정·범위 좁히기 배지, 최근 검토 방향, 정정 전 관점 제외, 후보 3개를 확인했다. 두 주소의 브라우저 세션이 분리되고 baseline에 상태 DOM이 없는 것도 확인했으며 콘솔 예외는 없었다. 이는 실제 저장 결과의 화면 검증이며 새로운 참여자 실험을 대신하지 않는다. 현재 진행 중인 기존 사용 세션의 과거 추정/응답은 재작성하지 않는다.

로컬 baseline은 Python 170개/JavaScript 37개 검사를 통과했다. 사본의 proposed 경로와 원본 v4의 동일 5턴 fixture를 비교하여 11개 모델 호출의 프롬프트·맥락·계획·응답이 같음을 확인했다(UUID·시각·경과 시간만 정규화). baseline 생성 맥락의 추정 차단, 정정의 직접 답변과 설명/비교 후보 유지도 별도 검사했다.

## 데이터와 범위

정책/판단 기준/상세 패널 버전은 `11.11-v4`, 공통 응답 형식은 `11.10-v3`이다. DB 테이블과 기존 로그는 유지한다. 표시되는 검토 진전과 모델이 제안하는 현상/관점 해석의 타당성은 실제 참여자 평가가 필요하다. 최종 연구 문제의 채택, 개념 이해, 어려움 해소는 클릭만으로 판정하지 않는다.

Baseline은 로컬에서 공통 추정 기준과 상태와 무관한 응답 검사를 맞추며, 추정 결과는 분석용으로만 저장한다. 상태 패널·상태 기반 생성·정리 제안은 계속 제외한다. Baseline 브랜치는 GitHub에 올리지 않는다.
