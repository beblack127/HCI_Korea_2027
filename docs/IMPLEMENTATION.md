# 11.09 초기 구현의 결정 사항

## 11.11-v3: 표현·미확인 어려움·행동 기반 지원

- `difficulty.py`: 확장된 난점 표현과 부정·가정·제3자 필터, 기술 원리와 관심 관련성 구분, 네 유형에 넣지 못한 명시적 난점의 `unspecified` 유보를 제공합니다. 의미 분류와 보수적 언어 휴리스틱의 결합이며 모든 표현의 정확한 이해를 보장하지 않습니다.
- `behavior.py`: 선택+실행을 묶고 제목 정규화 키로 주제를 추적합니다. 실제 왕복, 성공 응답 뒤 반복 질문·설명 방식 수정, 같은 주제의 구체화, 검색·서로 다른 문헌 검토를 별도 단서 종류로 구성합니다. 제목이 다른 동의어의 완전한 의미 통합은 포함하지 않습니다.
- 복수 종류 단서·최신성·세 개 이상의 사용자 이벤트 근거를 충족한 지원은 `possible`로만 구성합니다. 단일 질문·재방문, 오류 후 재전송, 대기 시간, 단일 문헌 행동은 이를 만들지 않습니다. 시스템 후보 반복은 사용자 어려움과 분리한 `support_issues`입니다.
- 이전에 표현한 어려움은 `pending_difficulties`와 화면의 `unconfirmed` 표시로 유지합니다. 과거 근거를 새로운 표현으로 확정하지 않습니다. 과거 기록은 수정하지 않고 다음 추정에서 기술적 연결의 유형을 보정하며 원래 유형과 ID를 보존합니다.
- 기존 버튼 요청을 우선한 채 `support_adjustment`로 해당 답변의 예시·비교 기준·구체화 연결을 조정합니다. 원인 미상 난점의 `orient`는 내부 모드이며 추가 선택지는 없습니다. 후보 3개·짧은 대화·상세 상태·정리 기능을 유지합니다.
- 상태·지원 타당성은 사용자 연구로 검증해야 합니다. 상세 초기 문턱과 제한은 현재 README 6·7절을 따릅니다.

## 11.11-v2: 정리 준비도와 사용자 확인

- `core/readiness.py`에서 검증된 문제·관점/범위·동일 방향 후속 탐색을 검사합니다. 기존 방향 상태·어려움 차원과 분리하며 클릭·시간·문헌 수를 종료 기준으로 삼지 않습니다.
- 방향 제안·둘러보기·구체화 응답에서 조건부 버튼 하나를 제시합니다. 같은 문제·범위의 제안은 반복하지 않으며 직접 어려움·별도 설명 요청에서는 제안을 미룹니다. 평소 둘러보기·구체화하기 UI를 유지합니다.
- `action=wrapup`은 현재 제안의 서명을 확인한 사용자 선택입니다. 새 의도적 입력이 아직 추정되지 않았거나 현재 상태와 서명이 다르면 거부합니다. 같은 세션 잠금과 request_id 캐시를 사용합니다.
- 정리 결과는 검증한 상태에서 구성하며 새 모델·검색 호출을 하지 않습니다. 단계·어려움 해소를 자동 판정하지 않고 원본 추정도 덮어쓰지 않습니다. 이후 대화에서는 다시 탐색과 후보 추천을 이어갈 수 있습니다.
- 준비도는 설계 휴리스틱입니다. 의미적 방향 연속성과 정리 시점의 타당성은 사용자 연구에서 별도 검증해야 합니다. 어려움 판정의 유형·보수적 기준은 이번 변경의 범위에 포함하지 않았습니다.

## 데이터 → 상태 → 지원의 구분

1. **관찰**: 사용자 발화, 후보 선택/둘러보기/구체화하기, 수동 검색, 초록 펼치기, 원문 클릭, 저장/해제를 순서 있는 이벤트로 저장한다.
2. **해석**: 현재 관심, 드러난 연구 문제, 방향 정립 정도, 어려움 유형, 변화, 미결정 요소를 LLM이 반환한다. 각 근거는 관찰 이벤트 ID를 참조한다.
3. **검증**: 현재 세션의 이벤트와 정확한 원문 인용을 확인한다. 연구 문제에는 문제를 드러내는 표현과 내용어의 연결을, 직접 어려움에는 유형에 맞는 난점 표현을 보수적으로 검사한다. 키워드의 임의 구체화·도움 요청의 어려움 오인·부정 표현 일부만 인용하는 경우를 방어한다. 이 검사는 의미적 진실이나 인지 상태의 타당성을 보장하지 않는다.
4. **지원 정책**: 이번의 명시적 요청·둘러보기·구체화하기를 우선한다. 지원 모드는 요청에 맞추고 키워드 후보는 항상 기본 3개 제공한다. 요청이 모호하면 현재 관심과 가까운 방향을 제안한다. 상태와 지원 폭을 동일시하지 않는다.
5. **상태 저장과 생성**: 상태·정책·기본 다음 행동을 먼저 저장한다. 응답은 상태 요약 → 필요한 도움 하나 → 다음 행동과 이유이다. 후보는 모든 턴에서 이번 지원 내용과 연결해 제공한다. 문헌 요청일 때만 보조 OpenAlex 검색을 수행한다. 응답 실패 시 상태는 error 표시와 함께 보존한다.

## 구분해 기록하는 것

- 사용자 입력/행동과 시스템 제안/추정을 서로 다른 이벤트·테이블로 저장한다.
- 상태의 `through_event_id`는 어느 관찰까지 포함했는지 표시한다.
- 상태 갱신 이후 새 논문 행동은 바로 이력에 추가되지만 재생성을 일으키지 않는다. 다음 의도적 입력에서 반영한다.
- 논문 ID는 OpenAlex ID를 유지한다. URL/제목 문자열을 ID로 대체하지 않는다.
- 원문 링크의 클릭을 실제 읽기로 기록하지 않는다.
- 형식 검증 전 LLM의 구조화 출력도 `raw_estimate`로 남겨 정규화 후 결과와 구분한다. 비공개 사고 과정은 요청·저장하지 않는다.
- 모델, 정책 버전, 판단 기준 버전, 프롬프트 해시를 추정 이력에 기록하고 사용된 프롬프트·기준 사본은 `data/prompt_versions/`에 보관한다.

## 11.11-v1: 선택한 주제를 알아보는 둘러보기

- `latest_action=browse`는 전용 지원 모드 `browse`와 `recommendation_focus=selected_direction`을 사용합니다. 설명을 생략하는 `directions`와 분리하고 선택한 후보를 응답 맥락에 유지합니다. 상태 추정 기준은 변경하지 않습니다.
- 본문에는 해당 주제가 다루는 문제와 구체적인 상황 예시를 기본 2문장으로 설명하고, 다음 행동은 서로 다른 측면을 알아보는 행동 하나로 제안합니다. 후보 3개는 선택 전의 형제 후보 목록으로 되돌아가지 않고 선택한 주제와 연결된 문제·상황을 보여줍니다. 이 관련성은 프롬프트 지침이며 서버가 의미적으로 증명하는 조건은 아닙니다.
- `core/browse.py`는 정규화한 제목과 설명으로 후보 수·중복·빈 설명/검색어·직전 3개 세트 반복을 검사합니다. 새 ID, 순서, 공백/문장부호 차이로 반복을 숨길 수 없습니다. 동의어 수준의 의미적 반복이나 관련성까지 판별하지는 않습니다.
- 내용 검사 실패에 한해서 응답 생성만 최대 한 번 재호출하고 검사 결과를 `provenance.browse_validation`에 남깁니다. 정상 요청은 두 모델 호출을 유지합니다. API 오류 자체는 이 재생성 대상이 아닙니다. 반복 실패·API 실패 모두 추정 상태와 사용자 입력을 보존합니다.
- 비교 요청은 기존 후보를 유지해도 됩니다. 반복 검사는 `browse` 모드에만 적용합니다. 둘러보기 클릭만으로 이해·동의·연구 문제 확정·어려움 해결을 가정하지 않습니다. 대화·상태 패널 및 검색의 배치는 유지합니다.

## v2: 응답 지연과 검색 연결

- 상태 추정 입력은 최근 사용자 관찰 160개(+첫 질의), 최근 대화 8개로 제한한다. 생성 이벤트에 중첩된 `raw_estimate`, 검증 기록, 이전 응답 원본은 관찰 목록에서 제외한다. 전체 원시 로그와 추정 이력은 그대로 보존한다.
- 최근 대화의 문헌은 ID·제목만 유지하고 중복 초록은 제거한다. 실제 상호작용한 문헌의 초록은 별도 관찰 문헌 맥락으로 추정에 전달한다.
- 답변 생성에는 검증된 상태·정책·최근 대화·이번 선택·제공 문헌만 전달한다. 연구자가 정의한 정책과 상태 검증은 기존처럼 별도 단계로 유지한다.
- 요청별 단계와 경과 시간을 메모리에 잠시 보관하고, 현재 세션에서만 조회한다. 이는 처리 단계이며 LLM의 내부 사고 과정을 뜻하지 않는다. 실제 소요 시간과 입력 길이를 추정 provenance에 남긴다.
- 개별 모델 응답 대기는 300초로 변경했다. 화면은 초·분 타이머를 표시하고, 90초가 지나도 요청을 중단하지 않는다.
- 후보마다 영어 검색 키워드를 출력한다. 후보 선택/둘러보기/구체화하기와 논문 검색 버튼은 분리했다. 문헌 조회만으로 새 상태 추정을 실행하지 않는다.
- 시작·종료 연도를 각각 입력할 수 있으며, 양쪽 생략·한쪽 생략·같은 연도를 지원한다. API 필터, 캐시 키, 활동 로그와 새로고침 복원에 두 값을 함께 보존한다.
- Figma 파일을 생성하거나 기존 디자인 파일을 수정한 업데이트는 아니다. 실제 HTML/CSS 인터페이스에 패널의 층위·테두리·그림자·타이포그래피를 적용했다.

## v3: 어려움의 표현과 지원

- 저장된 추정에서 캡처의 어려움은 이미 connection/expressed로 존재했으나, 패널 아래의 작은 확인 항목으로 제시되어 가시성이 낮았습니다.
- 어려움을 현재 상태 카드의 배지와 바로 아래 상세 영역에 제시합니다. 실제 evidence_ids에 연결된 사용자 발화를 최대 180자로 발췌합니다.
- formulation은 연구 문제로의 구체화 어려움이며, concept·connection·selection과 구별되는 잠정 분류입니다. 방향 형성과 공존할 수 있습니다.
- 다른 주제 요청/둘러보기 자체로 어려움을 확정하지 않도록 추정 지침을 명시했습니다. 이전 어려움이 이어진다고 추정할 경우 실제 이전 발화를 참조하도록 합니다.
- 새 분류는 JSON schema, 상태 검증, 추정 기준, 프롬프트, 정책, UI와 함께 갱신했습니다. 형식·참조 검증이 심리적 타당성을 보장하지 않는다는 범위는 동일합니다.

## v4: 질문의 즉시 표시와 상태별 색

- 전송 직후의 로컬 말풍선은 서버 관찰 기록과 구분합니다. 서버 응답/중간 스냅샷의 request_id로 확인된 말풍선을 대체합니다. 실제 상태 추정은 서버에 기록된 관찰만 사용합니다.
- 서버 오류와 연결 오류를 구별해 질문을 보존합니다. 재시도는 같은 요청 ID를 사용하므로 서버 이벤트와 메시지를 중복 생성하지 않습니다. 같은 문장이라도 사용자가 별도로 다시 전송하면 다른 요청입니다.
- 각 메시지의 요청 ID는 기존 message_key의 역할 접미사를 제거해 제공합니다. 기존 답변의 difficulty_status/types는 같은 세션·요청의 검증된 추정에서 조회합니다. 원본 메시지나 추정을 다시 쓰지 않습니다.
- 붉은 색은 수치화된 어려움의 심각도를 뜻하지 않습니다. expressed/possible 구분은 기존 문구로 유지합니다. unknown/clear에는 기본 녹색을 사용합니다.


## 11.10-v1: 근거·어려움 변화·응답 구조 (이전 정책)

- 상태의 관찰 문구는 실제 서버 로그에서 재구성한다. 모델은 해석을 제안하며 연구 문제와 직접 어려움에는 정확한 원문 인용이 필요하다. 문제 표현·내용어 연결·난점 표현·부정/해소 맥락을 보수적으로 검사한다. 표시되는 연구 문제는 사용자 원문 안의 발췌를 사용한다.
- 상태 요약은 검증한 방향과 어려움으로 서버가 구성한다. 검사에서 유보한 추정을 모델의 요약 문구가 다시 단정하지 못하게 한다. 정해진 표현 검사는 자연어의 모든 의미를 이해하지 못하므로 사용자 데이터 기반 검증이 필요하다.
- behavior_signals는 최근 30개 관찰의 후보 재방문, 검색 변경과 문헌 검토 조합이다. 단독 패턴은 어려움으로 확정하지 않는다. 맥락의 난점 표현 또는 여러 조합이 함께 있는 경우에도 possible만 허용한다. 열람·저장은 이해/확정의 증거가 아니다.
- difficulty_history는 주제와 근거·지원 제공 여부를 보관하고 active/unconfirmed/resolved/out_of_scope를 구분한다. 현재 상태에는 최근 20건을 제공하며 전체 과거 추정은 export에 남는다. 해소에는 후속 사용자 표현이 필요하며 여러 어려움이 있으면 유형을 구분한다.
- 도움 요청은 support_request, 후보 생성 요청은 recommendation_intent이다. 모호하면 기존 후보를 유지한다. 현재 후보는 최근 대화 8개 밖으로 밀려나도 available_directions로 전달한다. 이것은 사용자 관찰 증거와 구분한다.
- 응답은 assistance 하나와 next_step/next_step_reason을 사용한다. 상태 요약은 서버가 붙이고 필요하지 않은 설명은 비운다. 새 후보가 없는 턴에는 빈 선택 영역 대신 기존 후보로 이동하는 연결만 제공한다.
- 개념 어려움의 해소가 확인되지 않으면 개념 검토에 머무르는 기본 다음 행동을 사용한다. 사용자가 확정을 요청하지 않았으면 선택·확정을 재촉하는 생성 문구를 비교·검토 행동으로 보정한다.
- state.response_status는 generating/completed/error이며 검증한 상태를 먼저 저장한다. 진행 조회는 해당 세션·요청의 상태만 반환한다. 같은 관찰과 프롬프트의 재시도는 저장된 추정을 재사용한다. 원본 관찰은 중복 생성하지 않는다.
- 기존 데이터베이스 스키마·API 키·과거 메시지와 추정은 유지한다. 새 상태 필드는 새 턴부터 적용하며 원본을 소급 변환하지 않는다.


## 11.10-v2: 키워드 추천의 지속 제공

- 실제 사용 중 후보가 없는 답변에서 다음 탐색이 막막하다는 피드백을 반영한다. 개념·예시·연결·비교·문헌 안내를 포함한 모든 턴에서 기본 3개의 주제/키워드 후보를 제공한다.
- support_request와 어려움 추정은 바꾸지 않는다. recommendation_intent는 새 방향을 명시적으로 요청했는지를 구분하며, 후보 표시 여부를 결정하지 않는다.
- 정책의 recommendation_focus로 개념 연결 / 관심과 연결 / 기존 후보 비교 / 문헌 연결 / 연구 문제 구체화 / 방향 제안을 구분한다. 기존 후보를 비교할 때 무관한 분야로 바꾸지 않는다.
- 답변은 상태 요약 → 필요한 도움 하나 → 다음 행동과 이유 → 후보 카드이다. 본문은 간결하게 유지하며 후보의 존재를 이해나 해소의 근거로 삼지 않는다.
- 개념 어려움이 미확인 상태이면 후보가 제시돼도 다음 행동은 해당 개념 검토에 머문다. 명시적인 새 연구 방향 요청은 우선한다.
- 과거 후보가 없었던 응답도 그대로 열람할 수 있도록 기존 렌더링은 호환 유지한다. 과거 응답을 소급 생성하지 않는다.


## 11.10-v3: 짧은 대화와 상세 상태 패널

- core/presentation.py는 검증된 상태와 원본 관찰에서 chat_summary, recent_change, clarified_aspects, observed_directions, open_questions, flow_summary를 구성한다. 대화와 패널이 별도 상태를 추정하지 않는다.
- clarified_aspects는 모델이 제안한 관심·관점·범위의 정확한 사용자 인용만 허용한다. 연구 문제는 기존 검증을 통과한 사용자 표현을 사용한다. 이전 인용은 실제 세션의 원본 발화가 있는 경우에만 유지하며 명시적 주제 변경에서는 범위를 초기화한다.
- 최근 변화와 흐름은 실제 사용자 입력·선택·문헌 활동에서 구성한다. 구체화하기 선택은 탐색 지원의 요청이며 방향 형성을 자동 확정하지 않는다.
- response.state_summary는 state.chat_summary, 패널 상단 요약은 state.summary이다. 같은 상태를 다른 길이로 표현한다. 상세 이유 next_step_reason은 대화에서 숨기고 패널에 표시한다.
- assistance.body는 기본 2문장·320자 이내의 미리보기다. 원문 설명은 assistance.details로 보존하여 펼쳐 볼 수 있다. 사용자가 자세히/상세히/단계별 설명을 명시적으로 요청하면 기본 펼침이다. 긴 원문을 삭제하지 않는다.
- 후보 설명은 한 문장·120자 이내다. relation과 relation_label이 현재 방향과의 관계를 표시한다. 후보별 이유는 state.recommendation_context에 함께 저장하고 패널에서 확인한다.
- 기존 답변은 원래 데이터 형식으로 계속 표시한다. 새 상태와 표현은 새 턴부터 적용한다. 말풍선·패널 배치·API 키·기존 SQLite 데이터는 유지한다.
